# Кабинет владельца GlobalStay — первый срез

Дата: 2026-09-20  
Статус: правки после ревью, ждёт повторного ревью файла  
Продукт: веб-сайт для владельцев жилья  
Макет: [Booking (Figma)](https://www.figma.com/design/zqPAmK0qrRQtqMp5IP3K5u/Booking?node-id=1-16219)  
Секция макета: `1:16219` «Веб-сайт для владельцев жилья»  
ТЗ: [`docs/technical spec.md`](../../technical%20spec.md) — раздел «Веб-сайт для владельцев жилья»  
Прод-домен: `website.booking.vallome.ru`  
PocketBase (позже): `https://pb.booking.vallome.ru/_/`

## 1. Цель

Собрать десктоп-кабинет владельца **пиксель-в-пиксель** по Figma для одного вертикального среза: вход в систему, список объявлений, мастер создания и отправка на модерацию. Остальные разделы кабинета видны в сайдбаре, но открывают заглушку.

PocketBase в этом срезе не подключаем. Данные живут в мок-адаптере (`localStorage`) за тем же интерфейсом API, который позже закроет PocketBase.

## 2. Границы среза

### Входит

- Стек: Vite + React + TypeScript + React Router, деплой статики через **Caddy** (nginx нет).
- Дизайн-система примитивов из Figma, затем экраны из этих примитивов.
- Авторизация: вход, регистрация, восстановление пароля (только UI + мок), онбординг профиля (фото необязательно; имя и телефон обязательны).
- Оболочка кабинета: сайдбар 235px, шапка, логотип GlobalStay.
- Список объявлений: вкладки «Все / Опубликованы / На модерации / Архив», поиск, пустое состояние, карточки.
- Кнопка «Импорт из TravelLine» на списке — как в макете, по клику заглушка «Импорт появится позже». Поля API-ключа TravelLine в этом срезе нет (оно на полном профиле).
- Мастер создания: 6 шагов + предпросмотр (`1:20382`) с действиями кадра: править, удалить, сохранить в архив, отправить на модерацию.
- Пункт меню карточки «Опубликовать» **рисуем как в макете** (`1:18991`, кадр `1:22504`). Клик **не** меняет статус и показывает заглушку: «Публикацию выполняет администратор, раздел появится позже».
- Заглушки: `/bookings`, `/chats`, `/notifications`, `/profile` — каркас кабинета и текст «Раздел появится позже». Выход только с `/profile`: модалка `1:22639`, подтверждение → `logout` → `/login`.
- Viewport **< 1280px**: полноэкранная заглушка «Откройте сайт с компьютера». Данные не трогаем. Подпись на кадре `1:22650` про планшет игнорируем сознательно.
- Документация в `docs/` (см. §10).

### Не входит (следующие циклы)

- Настоящий PocketBase, SMS, почта, пуши.
- Бронирования, календарь занятости, чаты, уведомления, полноценный профиль, вывод средств.
- Интеграция TravelLine (кнопка не вызывает API).
- Публикация объявления администратором и повторная публикация из архива. Мок **никогда** не ставит `published`. Вкладка «Опубликованы» всегда с пустым состоянием. Статуса `rejected` в срезе нет.
- Отдельное поле «тип размещения» из ТЗ: на кадре шага 1 (`1:19264`) его нет — не заводим.
- Клиентское приложение и админка.
- Адаптив планшет/телефон, кроме заглушки «откройте с компьютера».
- Секреты и admin-токен PB в клиенте — запрещены в любом цикле.

ТЗ целиком не реализуем. Этот файл — источник правды для **первого среза**; полное ТЗ остаётся картой продукта.

## 3. Архитектура

```
src/
  app/          маршруты, провайдер сессии, порог ширины окна
  ui/           Button, Input, Sidebar, Tabs, Search, ListingCard,
                EmptyState, Modal, WizardSteps
  pages/        экраны среза и заглушки разделов
  api/          интерфейсы AuthApi, ListingsApi + mock-адаптер
  config/       публичные константы (комиссия, ширина, бренд, токены)
```

Правила слоёв:

- Страницы вызывают только `api/*`. Ни `localStorage`, ни PocketBase в компонентах.
- `ui/*` не знает про объявления и сессию — только пропсы.
- Мок и будущий PB-адаптер реализуют один интерфейс. Смена адаптера — правка одной фабрики, не экранов.
- `SERVICE_COMMISSION_RATE` живёт **только** в `src/config`. В JSX и страницах число `0.09` не копируем.

Сборка: `vite build` → `dist/`. Caddy на VPS отдаёт `dist`, неизвестный путь → `index.html` (SPA). Dev-сервер Vite на VPS не выставляем.

Публичные env (префикс `VITE_`) — только то, что можно светить в DevTools: например будущий URL PB. Пароли, admin-токен PB, SMTP, платежи — никогда.

## 4. Маршруты

| Путь | Экран | Доступ |
| --- | --- | --- |
| `/login` | Вход | гость |
| `/register` | Регистрация | гость |

| `/listings/:id/edit` | Тот же мастер по существующему id, шаг `?step=` | владелец объявления + онбординг |
| `/listings/:id/preview` | Предпросмотр | владелец, статусы `draft` / `moderation` / `archived` + онбординг |
| `/bookings` | Заглушка | авторизованный + онбординг |
| `/chats` | Заглушка | авторизованный + онбординг |
| `/notifications` | Заглушка | авторизованный + онбординг |
| `/profile` | Заглушка + «Выйти» | авторизованный + онбординг |
| `/` | редирект | `/listings` или `/login` или `/onboarding` |

Гарды:

- Неавторизованный на любой кабинет (включая заглушки, `edit`, `preview`) → `/login`.
- Авторизованный без онбординга на любой кабинет, включая заглушки → `/onboarding`.
- Авторизованный на `/login`, `/register`, `/forgot-password`, `/reset-password` → `/listings`, если онбординг пройден, иначе `/onboarding`.
- Чужой или неизвестный `:id` на `edit` и `preview` → `/listings`.
- `?step=` вне 1–6 → шаг 1.
- Битый или чужой reset-token: кадр ошибки у поля, сессию не создаём.
- «На модерацию» с неполного черновика не вызываем: те же проверки, что у «Далее» на каждом шаге.

## 7. Данные

Типы ниже — **источник правды**, не ориентир.

```ts
type ListingStatus = "draft" | "moderation" | "published" | "archived";

type HousingType = "apartment" | "apartments" | "studio" | "house" | "room";
// подписи: Квартира | Апартаменты | Студия | Дом | Комната
// в открытом селекте Figma списка нет; в предпросмотре пример — «Квартира».
// отдельного «типа размещения» из ТЗ нет.

type AmenityId =
  | "wifi" | "tv" | "ac" | "heater" | "hairdryer"
  | "iron" | "kitchen" | "washer" | "dishes";

  | "breakfast" | "pool" | "fireplace" | "smoking"
  | "gym" | "selfCheckIn" | "sauna" | "parking";

interface Session {
  userId: string;
  email: string;
  name: string;
  phone: string;
  photoUrl?: string;
  onboardingComplete: boolean;
}

interface Listing {
  id: string;
  ownerId: string;
  status: ListingStatus;
  title: string;
  address: string;
  housingType: HousingType;
  description: string;
  photos: string[];

interface ListingsApi {
```

Подписи удобств (кадр `1:19568`): Wifi, Телевизор, Кондиционер, Обогреватель, Фен, Утюг, Кухня, Стиральная машина, Посуда.  
Доп. характеристики: Завтраки, Бассейн, Камин, Разрешено курение, Спортзал, Самостоятельное заселение, Сауна, Парковка.  
Шаг 3 закрывается при нуле выбранных чипсов (валидно).

### Валидация auth

- Email: `trim + lower`, непустой, формат `локаль@домен.tld`. Повтор в `gs.users` — «Такой email уже зарегистрирован».
- Пароль: ≥ 8 символов. На регистрации второе поле как в Figma; несовпадение — ошибка у поля подтверждения.
- Телефон: `+7` и 10 цифр, маска `+7 (XXX) XXX-XX-XX`.
- Имя: trim, 2–50 символов.
- Тексты ошибок — с кадров входа/регистрации/онбординга; если на кадре пусто — «Обязательное поле».

### Мок

- Ключи `localStorage`: `gs.session`, `gs.users`, `gs.listings`.
- В `gs.users` храним `passwordHash = hex(SHA-256(utf8(password)))` без соли (только мок). В `Session` и в React-стейте после submit пароля нет. Value пароля в DOM после ухода со страницы не восстанавливаем.
- При подключении PB ключи `gs.users`, `gs.session`, `gs.listings` удаляем.
- Старт с пустым списком. Сидов нет. Созданное объявление переживает перезагрузку.
- Поиск: `query` trim, без учёта регистра, по `title` и `address`, вместе с вкладкой. Debounce не требуется.
- Фото: JPEG/PNG/WebP; минимум 6, максимум 9 слотов как на `1:19396` (1 большое + 8 малых). Первый файл — обложка карточки и предпросмотра. Перед записью в `localStorage` сжимаем в JPEG, длинная сторона ≤ 1600px. Квота превышена — баннер §8, шаг не сохранён.
- Черновик пишем на успешный «Далее» или «Назад» с валидными полями текущего шага, не на каждый keypress.

### Комиссия (сознательное отклонение от ТЗ)

ТЗ: владелец указывает стоимость **для клиента**.  
**В срезе иначе:** владелец вводит **базовую** цену; цена для клиента только для чтения = база + комиссия. Ставка 9%.

Формула (только `src/config`):

`commission = Math.round(base * SERVICE_COMMISSION_RATE)` где `SERVICE_COMMISSION_RATE = 0.09`  
`clientPrice = base + commission`  
Пример: 3500 → 315 → 3815. Цифры 3500 / 320 в Figma — макетный пример, не формула.

### Машина статусов

| Было | Действие | Стало |
| --- | --- | --- |
| нет id | первый успешный «Далее» на шаге 1 | `draft` + id, URL `/listings/:id/edit`. Незаполненные шаги 2–6: `photos []`, чипсы `[]`, `maxGuests 0`, булевы `false`, строки `""`, цены `0`, `uniquePrices []` |
| `draft` | «На модерацию» с предпросмотра (все шаги валидны) | `moderation` |
| `moderation` | правка и `saveDraft` | поля пишем, статус **остаётся** `moderation` |
| `moderation` | повторный submit | идемпотентно, статус тот же |
| любой, кроме удаления | «В архив» | `archived` |
| `archived` | «На модерацию» | снова `moderation` |
| любой | удалить (предпросмотр или меню карточки) | запись снимаем, `/listings` |

`published` мок не выставляет. «Опубликовать» в меню — заглушка, статус не меняет.

Вкладки: `all` — все кроме чужих; `published` — пусто; `moderation` / `archived` — по статусу. Черновик виден во «Все», во «На модерации» его нет.

### Поля мастера

1. **Описание** (`1:19264`): название, адрес, вид жилья (enum выше), описание ≤ 500.
2. **Фото** (`1:19396`, `1:19479`): 6–9 файлов.
3. **Удобства** (`1:19568`): две группы чипсов, обе необязательны.
4. **Правила:** макс. гостей ≥ 1, животные да/нет, отмена да/нет, время заезда/выезда (как на предпросмотре: 14:00 / 12:00 — плейсхолдер, не дефолт обязательный; пустое время — ошибка «Обязательное поле»).
5. **Дополнительное** (`1:19891`): как попасть внутрь, правила проживания, доп. информация — каждое поле ≤ 500 (счётчики `0/500` на кадре).
6. **Стоимость** (`1:20055`, `1:20147`, `1:20254`): три базовые цены — сутки, от 14 дней, от 28 дней. Для каждой — комиссия и цена для клиента. Тоггл уникальных дат: массив `{ date: YYYY-MM-DD; base: number }` — **одна** база на дату, как на кадрах (не три цены на дату). Комиссия на дату — та же формула. Несколько строк, удаление, «добавить». Пустая дата или `base ≤ 0` — ошибка у поля, шаг не закрываем.

Предпросмотр: кадр `1:20382`.  
«Отправить на модерацию» → таблица статусов + экран `1:22257`.  
«Править» → `/listings/:id/edit`.

TravelLine, «Опубликовать» и заглушки разделов **не** вызывают `ListingsApi` / `AuthApi`, кроме подтверждённого «Выйти» (`logout`).

## 8. Ошибки и крайние случаи

- Неверный логин — ошибка у поля, как состояния кадров входа.
- Пустые обязательные поля — ошибка у поля; запасной текст «Обязательное поле».
- Меньше 6 фото — «Добавьте ещё N фото». Больше 9 — слот не добавляем.
- Переполнен `localStorage` — баннер «Не удалось сохранить, попробуйте ещё раз».
- Битая JSON-сессия — `logout` и `/login`.
- Узкое окно — только заглушка.

Письма нет. После ввода email — кадр успеха и на нём демо-ссылка «Задать новый пароль» → `/reset-password?token=...`.

- мок: регистрация, повтор email, вход, ошибка входа, онбординг, черновик после шага 1, модерация, повторный submit, правка с модерации (статус не сбрасывается), архив → снова модерация, удаление, фильтр вкладок, поиск по названию/адресу без учёта регистра;

- «Опубликовать» не ставит `published`.

Ручная сверка на ширине 1440 по таблице §5. Отдельно: 1280 — кабинет (не заглушка); 1279 — заглушка.

## 11. Безопасность (этот срез)

- Нет `VITE_` с секретами.
- Source maps в production-сборке выключены.
- Мок в `localStorage` — только этот браузер; это не продакшен-хранилище ПДн.
- Пользовательские строки (`description`, адрес, правила, имя, чаты в будущем) рендерим **только как text content** (React children / `textContent`). HTML и Markdown не интерпретируем.
- `photo` / аватар — только `img[src]` из data URL, который записал адаптер после сжатия. Сырой `src` из поля ввода не подставляем.
- Когда появится PB: в клиенте сессия пользователя, не admin-ключ; доступ режут правила коллекций.

## 12. Критерий готовности среза

1. Экраны таблицы §5 визуально совпадают с кадрами на ширине 1440.
2. Регистрация с валидными email / паролем ≥ 8 / подтверждением → онбординг имя + телефон → кабинет.
3. После шага 1 без submit карточка есть во «Все» со статусом «Черновик», во «На модерации» её нет.
4. Полный мастер → предпросмотр → «На модерацию» → перезагрузка → вкладка «На модерации».
5. Правка с модерации не снимает статус.
6. Архив → вкладка «Архив» → снова «На модерацию».
7. «Опубликовать» в меню не даёт `published`. Вкладка «Опубликованы» пустая.
8. Описание вида `<img src=x onerror=…>` на предпросмотре — видимый текст, не тег.
9. TravelLine и чужие пункты сайдбара открывают заглушку, сессия жива. Выход — модалка на `/profile`.
10. Ширина 1280 — кабинет; 1279 — заглушка.
11. Документы §10 на месте (кроме обновлённого README — его дополняем вместе с каркасом), секретов нет.
12. Тесты §9 зелёные.
